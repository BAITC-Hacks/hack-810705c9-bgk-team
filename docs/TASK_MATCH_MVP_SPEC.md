# Техническое задание: MVP «Мэтч задач»

| | |
|---|---|
| Основание | Кейс AI Sana «Рейтинг качества бизнес-задач и открытый выбор команд» |
| Срок | 5 часов, включая демонстрацию |
| Команда | 3–5 человек |
| Формат | Веб-приложение с работающей логикой |
| Дата | 23.09.2026 |

## 1. Назначение

Платформа подработки и практики для студентов на реальных бизнес-задачах.

| Сторона | Проблема | Что даёт платформа |
|---|---|---|
| Студенты (разработчики, аналитики, дизайнеры, ML, QA) | Нет доступа к подработке и практике; задания размытые | Грамотное задание: цель, данные, критерии приёмки, контакт. Портфолио с отзывом бизнеса |
| Бизнес | Задачи не решаются; не умеет ставить задачу исполнителю | Помощь в постановке задачи, выбор из нескольких команд, решение задачи |

**Цель MVP** — работающий сквозной сценарий: слабый черновик → уточнение → рост рейтинга → публикация → отклик команды → ручное решение бизнеса → подтверждённый этап.

## 2. Термины

| Термин | Значение |
|---|---|
| Задача | Запрос бизнеса к студентам |
| Карточка | Структурированное описание задачи |
| Узел | Элемент карточки с весом в рейтинге (17 узлов) |
| Рейтинг | 0–100, качество задания для студента |
| Уровень | Черновик / Рабочая / Готовая / Приоритетная |
| Прожарка | Диалог, в котором ИИ задаёт бизнесу вопросы исполнителя |
| Колода | Персональная подборка задач для команды или откликов для бизнеса со свайпами |
| Сетка | Альтернативный вид рекомендаций команды: плитки задач с кнопками вместо свайпов |
| Отклик | Предложение команды по задаче |
| Мэтч | Ручной выбор команды бизнесом |
| Этап | Критерий приёмки, который команда сдаёт, а бизнес подтверждает |
| Стартовый пакет | Материалы, контакт и первый этап для выбранной команды |
| Формат работы | Подработка, практика или оба |

## 3. Роли

| Роль | Возможности |
|---|---|
| Бизнес | Создать задачу, пройти прожарку, редактировать и подтвердить карточку, опубликовать, сравнить отклики, выбрать или отклонить, подтвердить этап |
| Команда | Смотреть каталог и рекомендации (колода или сетка), отправить отклик, получить стартовый пакет, сдать этап |

Регистрации нет. Роль выбирается переключателем в шапке и хранится в cookie.

## 4. Сквозной сценарий

| # | Шаг кейса | Реализация | Результат |
|---|---|---|---|
| 1 | Черновик | Бизнес вводит текст, тему и формат работы | `Task: draft` |
| 2 | Уточнение | Прожарка: ≥3 вопроса по открытым узлам | Ответы привязаны к узлам |
| 3 | Карточка | Поля из ответов, редактирование, подтверждение | `Field: confirmed` |
| 4 | Рейтинг | Расшифровка баллов, недостающие сведения, следующий шаг | Рейтинг и уровень |
| 5 | Каталог | «Подтвердить и опубликовать» | `Task: published`, место по рейтингу |
| 6 | Выбор студентов | Каталог, колода или сетка → отклик | `Proposal: submitted` |
| 7 | Выбор бизнеса | Список и сравнение откликов → выбрать / отклонить | `Proposal: accepted / rejected` |
| 8 | Результат | Команда сдаёт этап, бизнес подтверждает → +10 баллов команде | `Stage: confirmed` |

## 5. Функциональные требования

### 5.1. Конструктор задачи и прожарка

| ID | Требование |
|---|---|
| FR-1.1 | Черновик: свободный текст 20–2000 символов, тема из справочника, формат работы (подработка / практика / оба), условия оплаты — текстом, если выбрана подработка |
| FR-1.2 | После ввода система определяет, какие узлы закрыты черновиком, и предлагает поля карточки с цитатой-источником |
| FR-1.3 | Прожарка задаёт один вопрос за раз по открытым узлам в порядке: потребность → результат → критерии → данные и материалы → стек и роли → пользователи → связь |
| FR-1.4 | Прожарка задаёт **не менее 3 вопросов**. Если открытых узлов меньше трёх, вопросы задаются по узлам с неполными баллами |
| FR-1.5 | К вопросу — 2–4 варианта формата ответа, без цифр и фактов. Можно ответить своим текстом |
| FR-1.6 | Узел, закрытый черновиком или прошлым ответом, не спрашивается повторно |
| FR-1.7 | На расплывчатый ответ — ровно одно уточнение на узел |
| FR-1.8 | Ветки: «данных нет» → вопрос «кто соберёт и когда», узлы объёма и примера пропускаются; тип результата (бот / модель / макет) открывает профильный вопрос |
| FR-1.9 | В конце блока — сводка из цитат бизнеса и вопрос «Верно?». «Верно» подтверждает поля блока; «Исправить» открывает редактирование |
| FR-1.10 | Выйти из прожарки к публикации можно в любой момент |
| FR-1.11 | Ответ «нет / не применимо» с пояснением сохраняется и показывается исполнителям |
| FR-1.12 | Прожарка не спрашивает о доступах к системам бизнеса (стенды, ключи, учётные записи). Команда работает на выгрузках, примерах и документации |

### 5.2. Карточка задачи

| ID | Требование |
|---|---|
| FR-2.1 | Поля карточки (по кейсу): название, контекст, потребность, пользователи, данные, ограничения, ожидаемый результат, критерии успеха, контакт и формат взаимодействия |
| FR-2.2 | Дополнительные поля без баллов: тема, формат работы, условия оплаты, нужные роли, нужные навыки |
| FR-2.3 | Каждое поле редактируется вручную. Правка переводит поле в `suggested` до повторного подтверждения |
| FR-2.4 | Поле в состоянии `suggested` визуально отличается и не даёт баллов |
| FR-2.5 | Клик по полю показывает реплику бизнеса, из которой оно получено |
| FR-2.6 | Критерий успеха вводится структурно: метрика, порог, как проверить |
| FR-2.7 | Роли и навыки предлагаются из справочника; бизнес подтверждает список |
| FR-2.8 | Переключатель «Вид исполнителя» показывает карточку глазами команды |

### 5.3. Рейтинг

| ID | Требование |
|---|---|
| FR-3.1 | Рейтинг 0–100 по таблице узлов (раздел 6). Считает код, не ИИ |
| FR-3.2 | Баллы только за поля в состоянии `confirmed` |
| FR-3.3 | Расшифровка: строка на каждый узел — баллы, максимум, причина |
| FR-3.4 | Список недостающих сведений: открытые узлы с весом |
| FR-3.5 | Следующий шаг: самый весомый открытый узел и последствие («+15 → Рабочая») |
| FR-3.6 | Пересчёт после каждого подтверждения и правки |
| FR-3.7 | После пересчёта — панель «было → стало»: баллы, уровень, место в каталоге |
| FR-3.8 | Каждое изменение рейтинга пишется в историю |
| FR-3.9 | Формат работы и условия оплаты на рейтинг не влияют |

### 5.4. Публикация и каталог

| ID | Требование |
|---|---|
| FR-4.1 | «Подтвердить и опубликовать» показывает итоговую карточку. Неподтверждённые поля не публикуются |
| FR-4.2 | Публикация разрешена при любом рейтинге |
| FR-4.3 | Каталог показывает все опубликованные задачи всем командам |
| FR-4.4 | Сортировка: рейтинг по убыванию, при равенстве — дата публикации |
| FR-4.5 | Фильтры: тема, уровень готовности, роль, формат работы |
| FR-4.6 | Метки: 0–39 «Требует уточнения»; 90–100 — выделение и «Полностью готова» |
| FR-4.7 | На карточке в каталоге — блок «Пока неизвестно» с открытыми узлами |
| FR-4.8 | Откликнуться можно на задачу с любым рейтингом |

### 5.5. Рекомендации команды: колода или сетка

| ID | Требование |
|---|---|
| FR-5.1 | Профиль команды: название, роли, навыки, технологии, интересы, что ищет (подработка / практика / оба) |
| FR-5.2 | Совпадение `fit` считается кодом по ролям, навыкам с технологиями и теме (раздел 6.4) |
| FR-5.3 | В колоду попадают задачи: опубликованы, рейтинг ≥ 40, `fit` ≥ 0,5, формат подходит команде |
| FR-5.4 | Сортировка колоды: `0.7 × fit + 0.3 × рейтинг / 100` |
| FR-5.5 | На карточке — процент совпадения с объяснением: что совпало, чего не хватает |
| FR-5.6 | Свайп → открывает форму отклика; ← убирает задачу из колоды команды; ↑ отправляет бизнесу «не хватает сведений» по блоку |
| FR-5.7 | Жесты дублируются клавишами ← → ↑ и кнопками |
| FR-5.8 | Свайп ← не меняет рейтинг и место задачи в каталоге |
| FR-5.9 | Колода закончилась → ссылка «В каталоге ещё N задач» |
| FR-5.10 | Рекомендации не ограничивают каталог: вкладка «Все задачи» доступна всегда |
| FR-5.11 | Переключатель «Колода / Сетка» показывает один и тот же набор рекомендаций. Выбор вида сохраняется в cookie |
| FR-5.12 | Плитка сетки: название задачи, компания, совпадение, уровень и рейтинг, нужные роли, формат работы, «Пока неизвестно» |
| FR-5.13 | Кнопки плитки повторяют жесты колоды: «Откликнуться», «Не сейчас», «Не хватает сведений» |
| FR-5.14 | Сортировка сетки: по умолчанию как в колоде; переключение «по совпадению» / «по рейтингу» |
| FR-5.15 | Каталог «Все задачи» отображается той же сеткой, без процента совпадения в сортировке |

### 5.6. Отклики

| ID | Требование |
|---|---|
| FR-6.1 | Поля: идея решения, план, роли в команде, срок — обязательно; ссылка на прототип или репозиторий — необязательно, с проверкой URL |
| FR-6.2 | Для каждого критерия задачи — поле «как проверим» |
| FR-6.3 | Число откликов не ограничено |
| FR-6.4 | Одна команда — один активный отклик на задачу; отклик можно редактировать до решения бизнеса |

### 5.7. Выбор бизнеса и мэтч

| ID | Требование |
|---|---|
| FR-7.1 | Список откликов на задачу, сортировка по `fit`. Отклики с низким совпадением не скрываются, помечаются «совпадает частично» |
| FR-7.2 | Таблица сравнения «критерии × команды» |
| FR-7.3 | Колода откликов: → выбрать, ← отклонить, ↑ отложить. Те же действия — кнопками в списке |
| FR-7.4 | «Выбрать» требует подтверждения «Команда получит ваш контакт» |
| FR-7.5 | Отклонение требует причину: роли, стек, сроки, план, другое (с текстом) |
| FR-7.6 | Можно выбрать несколько команд или закрыть задачу без выбора |
| FR-7.7 | Автоматический выбор команды отсутствует |
| FR-7.8 | После выбора — экран мэтча для обеих сторон и стартовый пакет |
| FR-7.9 | Стартовый пакет собирается кодом из подтверждённых полей: материалы, стек, консультации, срок, условия оплаты или пометка о практике, первый этап |

### 5.8. Прогресс команды

| FR-8.2 | Команда сдаёт этап: ссылка и комментарий |
| FR-8.3 | Бизнес подтверждает этап или возвращает с комментарием |

## 6. Бизнес-правила

### 6.1. Узлы рейтинга

| Блок (кейс) | Узел | Вопрос исполнителя | Баллы | Условие засчитывания |
|---|---|---|:-:|---|
| Контекст и потребность (20) | `context.current` | Как процесс устроен сейчас? | 5 | подтверждено |
| | `context.size` | Насколько велика проблема? | 5 | есть число |
| | `context.change` | Что должно измениться? | 10 | подтверждено |
| Данные и материалы (20) | `data.what` | Какие данные, API, документация? | 10 | подтверждено |
| | `data.volume` | Объём, период? | 5 | есть число или период |
| | `data.sample` | Пример, схема, Swagger? | 5 | ≥3 строк таблицы или URL |
| Ожидаемый результат (15) | `result.artifact` | Что сдаём? | 10 | тип + описание |
| | `result.acceptance` | Как сдаём: демо, репозиторий, документация? | 5 | подтверждено |
| Критерии успеха (15) | `criteria.items` | По каким метрикам примете? | 5 × 3 | метрика + порог с числом = 5; без числа = 2 |
| Ограничения (10) | `constraints.deadline` | Срок? | 4 | дата или срок |
| | `constraints.stack` | Стек, роли? | 3 | подтверждены роли и навыки |
| | `constraints.other` | Иные границы: что нельзя, конфиденциальность? | 3 | подтверждено; «нет» засчитывается |
| Пользователи (10) | `users.role` | Кто пользователь? | 5 | подтверждено |
| | `users.scale` | Сколько их, в какой ситуации? | 5 | подтверждено |
| Связь с бизнесом (10) | `link.contact` | Кому писать? | 4 | email или мессенджер |
| | `link.cadence` | Формат консультаций? | 3 | подтверждено |
| | `link.response` | Порядок обратной связи: когда ответите на отклики? | 3 | число дней |

Ответ «нет / не применимо» — 0 баллов (кроме `constraints.other`).

### 6.2. Уровни

| Рейтинг | Уровень | Каталог | Колода |
|---|---|---|---|
| 0–39 | Черновик | Виден, метка «Требует уточнения» | Нет |
| 40–69 | Рабочая | Виден | Да |
| 70–89 | Готовая | Выше в сортировке | Да |
| 90–100 | Приоритетная | Выделен | Да, метка «Полностью готова» |

### 6.3. Ограничения геймификации

| Правило | Проверка |
|---|---|
| Рейтинг не зависит от популярности, размера компании, оплаты | Формула учитывает только узлы карточки |
| Низкий рейтинг не скрывает задачу | FR-4.3, FR-4.8 |
| Нет автоназначения | FR-7.7 |
| Нет баллов за количество действий | FR-6.3, FR-8.6; длина текста не учитывается |
| Одно уточнение на узел | FR-1.7 |

### 6.4. Совпадение

```
fit = 0.5 × доля нужных ролей, которые есть у команды
    + 0.3 × доля нужных навыков, которые есть в навыках или технологиях команды
    + 0.2 × (тема задачи в интересах команды ? 1 : 0)
```

Пустые нужные роли → задача не попадает в колоды; бизнес видит подсказку «+3 и попадание в колоды».

## 7. Требования к ИИ

| ID | Требование |
|---|---|
| AI-1 | Фреймворк — Mastra. Агенты: `griller` (формулирует вопрос и варианты формата), `card-extractor` (раскладывает ответ по узлам с цитатой), `classifier` (закрытые узлы, роли, навыки) |
| AI-2 | Workflow `analyze-draft`: черновик → закрытые узлы → предложенные поля → первый вопрос |
| AI-3 | Workflow `grill-turn`: классификация ответа → извлечение полей → решение (код) → формулировка вопроса. Состояние прожарки хранится в БД |
| AI-4 | Классификация узлов, ролей и навыков — агент `classifier` на OpenAI GPT-5.4 nano (`openai/gpt-5.4-nano`). Значения только из enum; при ошибке — заглушка на правилах |
| AI-5 | Ответы агентов — JSON по zod-схемам (`GrillQuestion`, `Extraction`) |
| AI-6 | Каждое поле от ИИ содержит `source_quote`. Цитата не найдена в тексте бизнеса → поле отбрасывается |
| AI-7 | Варианты ответа с цифрами отбрасываются |
| AI-8 | Невалидный JSON → 1 повтор → шаблонный вопрос узла |
| AI-9 | Таймаут: основная модель 15 с, nano 5 с → шаблон или заглушка; сценарий продолжается |
| AI-10 | Классификатор закрывает узел только с цитатой-доказательством из текста бизнеса |
| AI-11 | Роль или навык вне справочника → тег отбрасывается |
| AI-12 | ИИ не считает рейтинг, не выбирает команду, не скрывает задачи и отклики |
| AI-13 | Персональные признаки участников в ИИ не передаются |
| AI-14 | Журнал `AiLog`: промпт, вход, сырой ответ, `parse_ok`, отброшенные поля, `fallback_used`. Журнал доступен в интерфейсе для демонстрации |

Промпты агентов и схемы — в [TASK_MATCH_PLATFORM.md](TASK_MATCH_PLATFORM.md), раздел 8.

### 9.2. Состояния

| Сущность | Переходы |
|---|---|
| Task | `draft → published → in_work → closed` |
| Field | `empty → suggested → confirmed`; правка → `suggested` |
| Proposal | `submitted ↔ on_hold → accepted / rejected`; меняет только бизнес |
| Stage | `open → claimed → confirmed / returned → claimed` |

Уровень вычисляется из рейтинга и не хранится.

## 11. Приёмка

### 11.1. Тестовые сценарии

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| T-1 | Черновик логистики → 2 блока прожарки → публикация → отклик BotForge → выбор → этап | Рейтинг 24 → 44 → 59; мэтч; стартовый пакет; +10 команде |

| T-4 | Два расплывчатых ответа на один узел | Одно уточнение |

### 11.2. Демонстрация (5 минут)

1. Бизнес: слабый черновик логистики → прожарка с уточнением → рейтинг 24 → 59, клик по полю показывает источник.
2. Журнал ИИ: промпт, вход, выход, отброшенное поле.
3. Команда: колода, переключение на сетку, совпадение 92% с объяснением, отклик по критериям; каталог показывает черновики.
4. Бизнес: сравнение двух откликов, отклонение с причиной, выбор → мэтч → стартовый пакет.
5. Этап сдан и подтверждён: +10 и запись в портфолио.

## Приложение А. Эталонный пример

Черновик: «Мы логистическая компания. Операторы весь день отвечают клиентам, где их заказ. Хотим это автоматизировать. Контакт: it@logistics.example». Формат: подработка, «оплата за каждый принятый этап».

| Шаг | Что добавлено | Рейтинг | Уровень | Место |
|---|---|:-:|---|:-:|
| Черновик | Как сейчас, что изменить, пользователи — клиенты, контакт | 24 | Черновик | 6 |
| Дополнение 1 | Выгрузка статусов в CSV, документация API (Swagger), выгрузка чата за 6 мес. | 44 | Рабочая | 4 |
| Дополнение 2 (после уточнения) | ≥60% обращений без оператора, ответ < 3 с, «300 обращений в день» | 59 | Рабочая | 3 |
| Далее | Результат: Telegram-бот, демо + репозиторий | 74 | Готовая | 3 |
| Далее | Роли backend и бот-разработчик; Python, REST API, Telegram Bot API, Docker | 77 | Готовая | 2 |

Совпадение: BotForge — 92%, первая в колоде; DataBrew — 28%, только каталог.
