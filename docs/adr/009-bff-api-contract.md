# ADR-009: API BFF: REST route handlers, zod-валидация, ошибки и транзакционная согласованность

Дата: 2026-09-23
Статус: Proposed
Владелец: не назначен

## Контекст

ТЗ задаёт REST-поверхность `/api/*` (раздел 10, платформа 9.1). Все входы
валидируются zod, ошибки возвращаются с понятным текстом (NFR-4).

План работ (раздел 13) распределяет backend и два UI между разными людьми, а
AGENTS.md требует согласовать формы API до параллельной работы клиента и сервера.

В `presentation-layer` пока нет ни одного маршрута `app/api`. Next.js 16
позволяет и route handlers, и server actions. Серверные компоненты могут читать
данные напрямую, без HTTP.

Список эндпоинтов в ТЗ содержит `POST /api/tasks/:id/close` и `GET /api/ai-log`.
В платформе (9.1) их нет. Здесь источником истины считается ТЗ.

## Решение

1. **Контракт — route handlers по таблице раздела 10 ТЗ** в
   `apps/presentation-layer/app/api/**/route.ts`. Handler выполняет три шага:
   `getDemoActor()` ([ADR-008](008-demo-roles-and-access.md)), `schema.parse(body/query)`
   и вызов use-case. Бизнес-логики в handler нет.
2. **Чтение для страниц.** Серверные компоненты вызывают те же функции-запросы
   (`getCatalog`, `getRecommendations`, `getScore`), что и GET-handlers, без
   самозапроса по HTTP. Мутации из UI идут через `fetch` к route handlers (или
   через server action — тонкую обёртку над тем же use-case). В обоих случаях
   обязательны одна zod-схема и один use-case.
3. **Схемы запросов и ответов** лежат в `src/shared/api/contracts/*.ts` (zod),
   типы выводятся через `z.infer`. Обе UI-подкоманды и backend импортируют одни и
   те же схемы. Формы API фиксируются этим файлом до начала параллельной работы.
4. **Формат ошибок:** `{ error: { code, message, details? } }`, где `message`
   написан по-русски для человека.

   | Код HTTP | Когда |
   |---|---|
   | 400 | невалидный JSON |
   | 422 | нарушение zod-схемы или бизнес-валидации: отклонение без причины, URL отклика, длина черновика 20–2000 |
   | 403 | роль или владелец не совпадают |
   | 404 | сущность не найдена |
   | 409 | недопустимый переход состояния или устаревшая `version` |

   AI-сбои в ошибку не превращаются: ответ `200` с шаблонным вопросом и
   `fallbackUsed: true` ([ADR-003](003-ai-layer-contract.md)).
5. **Согласованность.** Каждый мутирующий use-case выполняется в одной транзакции
   Drizzle на `nextjs_db`. Переходы состояний делаются условными `UPDATE … WHERE status IN (…)`.
   Вызовы Mastra выполняются **вне** транзакции: сначала inference, затем короткая
   транзакция записи (ход, поля, `AiLog`, пересчёт). Долгий LLM-вызов не держит блокировки.
6. **Уточнения к таблице ТЗ, требующие согласования:**
   - `POST /api/tasks` возвращает `{ task, draftSummary, fallbackUsed }`, то есть
     сначала checkpoint черновика ([ADR-004](004-grill-state-and-field-lifecycle.md)),
     а не сразу первый вопрос;
   - `POST /grill/turn` принимает `{ answer, sessionVersion }` и возвращает
     `{ next: question|checkpoint|done, scoreDelta?, fallbackUsed }`;
   - для ручного подтверждения одного поля вне сводки блока используется
     `PATCH /fields/:node` с `{ action: 'confirm' }`. Иначе поле, исправленное в
     редакторе карточки, нельзя подтвердить, не проходя прожарку заново;
   - `PATCH /api/tasks/:id` (формат, оплата, теги) в таблице ТЗ отсутствует, но
     нужен для FR-1.1, FR-2.7 и T-7.

## Альтернативы

- **Только server actions без REST.** Меньше кода, но расходится с контрактом
  ТЗ (раздел 10). Такие вызовы неудобно проверять `curl`/скриптом для приёмки, и
  нет явной точки согласования форм. Отклонено как основной контракт; допустимо
  как обёртка.
- **tRPC или GraphQL.** Новая инфраструктура и зависимости без выигрыша для
  демо. Отклонено.
- **Транзакция, охватывающая вызов Mastra.** Держит соединение и блокировки до
  15–20 с. Отклонено.

## Последствия

- Плюс: один набор zod-схем даёт и NFR-4, и типы клиента, и точку согласования команды.
- Плюс: сценарии приёмки можно прогнать скриптом по HTTP ([ADR-010](010-acceptance-verification.md)).
- Минус: поверхность ТЗ расширяется тремя уточнениями (п. 6), их нужно
  подтвердить до начала параллельной работы.
- Риск: гонка между двумя вкладками при ходе прожарки. Закрывается `sessionVersion` → `409`.

## Затронутые модули и проверка

- `presentation-layer`: `app/api/**`, `src/shared/api/contracts`, `src/shared/api/errors.ts`, use-case в `src/features/*/api`.
- Проверка:
  - `bun run check-types` и `bun run lint` в `presentation-layer`;
  - HTTP-прогон: черновик 19 символов → `422` с текстом;
  - `reject` без причины → `422`;
  - повторный `turn` со старой версией → `409`;
  - T-13: при недоступной Mastra ход отвечает `200` с `fallbackUsed: true`.

## Допущения и открытые вопросы

- Подтвердить три уточнения API из п. 6 до начала параллельной работы.
- Мутации из UI: `fetch` к route handlers или server actions? Решение за
  разработчиками UI. Ограничение: один use-case и одна схема.
