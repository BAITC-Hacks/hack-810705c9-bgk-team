# ADR-007: Отклики, ручной выбор нескольких команд, фиксация этапов и однократные баллы

Дата: 2026-09-23
Статус: Proposed
Владелец: не назначен

## Контекст

Отклики:

- обязательные поля и «как проверим» по каждому критерию (FR-6.1, FR-6.2);
- один активный отклик команды на задачу, редактирование до решения (FR-6.4);
- статусы `submitted ↔ on_hold → accepted / rejected`, меняет только бизнес (раздел 9.2).

Решение бизнеса:

- список откликов, сортировка по `fit` без скрытия, таблица «критерии × команды» (FR-7.1, FR-7.2);
- подтверждение «Команда получит ваш контакт» при выборе (FR-7.4);
- обязательная причина отклонения (FR-7.5, T-16);
- можно выбрать несколько команд или закрыть задачу без выбора (FR-7.6, T-17, T-18);
- автоматического выбора нет (FR-7.7, AI-12);
- стартовый пакет собирается кодом из подтверждённых полей (FR-7.9, платформа 4).

Этапы и баллы:

- при выборе команды критерии фиксируются и становятся этапами (FR-8.1);
- жизненный цикл этапа: `open → claimed → confirmed / returned → claimed` (FR-8.2, FR-8.3);
- +10 за этап один раз (FR-8.4);
- запись в портфолио (FR-8.5);
- отклики, свайпы и мэтчи баллов не дают (FR-8.6).

Отдельной сущности «мэтч» в разделе 9.1 нет. T-18 требует «две записи мэтча, два набора этапов».

## Решение

1. **Мэтч = отклик в статусе `accepted`.** Отдельной таблицы нет. «Запись мэтча» —
   это строка `proposal` с `accepted_at` и снимком стартового пакета.
2. **Отклик.** `proposal (task_id, team_id, solution, plan, team_roles[], deadline, repo_url?, criteria_answers jsonb, fit, status, reject_reason?, reject_note?, decided_at?, kickoff jsonb?)`.
   - Частичный уникальный индекс `(task_id, team_id) WHERE status IN ('submitted','on_hold','accepted')`
     обеспечивает FR-6.4 на уровне БД.
   - `criteria_answers` ключуются по `criterion.id` и `task.criteria_version`.
   - `fit` фиксируется при создании и при правке отклика: сортировка FR-7.1 должна
     соответствовать профилю на момент отклика.
   - Отклик можно создать на задачу с любым рейтингом (FR-4.8), но только в статусе `published` или `in_work`.
3. **Решение бизнеса** — единый use-case `decideProposal(id, action, reason?)` с
   условным обновлением `UPDATE … WHERE status IN ('submitted','on_hold')`. При
   0 затронутых строк возвращается `409`.
   - `reject` без `reason` из enum (`roles|stack|deadline|plan|other`, для `other`
     обязателен текст) отклоняется в zod-валидации (`422`). В UI кнопка неактивна (T-16).
   - `on_hold` ↔ `submitted` разрешено в обе стороны.
   - `accept` в **одной транзакции**:
     1. `proposal.status = accepted`;
     2. если `task.status = published`, то `task.status = in_work`;
     3. стартовый пакет собирается `buildKickoff(confirmedFields, criteria)`, как
        в платформе (раздел 4), и сохраняется в `proposal.kickoff`;
     4. для каждого подтверждённого критерия создаётся `stage` со **снимком** его
        текста (`metric`, `threshold`, `how_to_check`) и `criteria_version`.

     Повторный выбор другой команды повторяет шаги 1, 3 и 4 (T-18).
4. **Закрытие без выбора** (`POST /tasks/:id/close`): разрешено при `status = published`,
   если нет `accepted`. В одной транзакции `task.status = closed`, а все
   `submitted` и `on_hold` становятся `rejected` с `reject_reason = 'task_closed'` (T-17).
5. **Этапы.** `stage (proposal_id, criterion_id, criteria_version, metric, threshold, how_to_check, status, report_url?, team_comment?, business_comment?, points, confirmed_at?)`.
   - `claim` выполняет команда-владелец отклика из `open|returned`, передавая ссылку и комментарий.
   - `return` выполняет бизнес из `claimed` с обязательным комментарием.
   - `confirm` выполняет бизнес командой
     `UPDATE stage SET status='confirmed', points=10, … WHERE id=:id AND status='claimed'`.
     Этап не может вернуться из `confirmed`, поэтому +10 начисляется один раз на
     этап (FR-8.4) без отдельного ledger.
6. **Баллы и портфолио команды считаются, а не хранятся.**
   `team_points = SUM(stage.points)` по подтверждённым этапам команды. Портфолио
   (FR-8.5) — выборка подтверждённых этапов с задачей, критерием, `team_roles`
   отклика и `business_comment` как отзывом. Ни один use-case откликов, свайпов и
   решений не пишет в баллы (FR-8.6).
7. **Сравнение откликов.** `GET /tasks/:id/proposals` возвращает список,
   отсортированный по `fit`, с меткой «совпадает частично» при `fit < 0.5`, и
   матрицу `criteria × proposals` из `criteria_answers`. Сортирует код, не AI.

## Альтернативы

- **Отдельная таблица `match`.** Дублирует `proposal.accepted`, и её придётся
  синхронизировать. Отклонено для MVP.
- **Этапы ссылаются на живой `criterion` без снимка.** Правка критериев после
  выбора молча изменила бы принятые условия, что нарушает «фиксируются» (FR-8.1). Отклонено.
- **Ledger `team_points_event`.** Нужен для начислений из разных источников. В MVP
  источник один, и уникальность обеспечивает переход состояния этапа. Отклонено как избыточное.
- **Стартовый пакет считается при каждом чтении.** Проще, но пакет меняется при
  правке карточки после мэтча. Отклонено в пользу снимка, согласованного со снимком этапов.

## Последствия

- Плюс: T-16, T-17 и T-18 и однократность баллов обеспечиваются ограничениями
  БД и условными `UPDATE`, без блокировок.
- Плюс: этапы и стартовый пакет не зависят от последующих правок карточки.
- Минус: после мэтча правки карточки не доходят до выбранной команды. Это
  сознательное следствие «фиксации».
- Риск: если бизнес меняет критерии, пока отклики на рассмотрении, `criteria_answers`
  ссылаются на старую `criteria_version`. Сравнение должно показывать
  несовпадение версий, а не терять ответы.

## Затронутые модули и проверка

- `presentation-layer`: `src/entities/{proposal,stage}/model`,
  `src/features/{submit-proposal,decide-proposal,close-task,stage-progress}/api`,
  `src/entities/task/model/kickoff.ts`. Таблицы появятся в миграции владельца схемы.
- Проверка:
  - API-прогоны T-16, T-17 и T-18;
  - повторный `confirm` этапа возвращает `409`, `team_points` не меняется;
  - юнит-тест `buildKickoff` на Приложении А: подработка → условия оплаты,
    практика → пометка об отчёте.

## Допущения и открытые вопросы

- Однократность начисления в первоисточниках сформулирована по-разному: FR-8.4 —
  «один раз на этап», платформа (7) — «один раз на критерий». При нескольких
  командах (T-18) это разные правила. Предложение следует FR-8.4.
- Можно ли редактировать отклик в `on_hold`? Предложение: да, так как `on_hold`
  не является решением (FR-6.4).
- Когда задача переходит `in_work → closed` и можно ли выбирать команды после
  `in_work`? ТЗ не определяет. Предложение: выбор доступен в `in_work`, закрытие
  из `in_work` — отдельный вопрос вне MVP.
- Контакт виден до мэтча? Мокап карточки исполнителя (платформа 4) показывает
  `Контакт:` в каталоге, тогда как FR-7.4 («Команда получит ваш контакт»)
  подразумевает, что контакт выдаётся только после выбора. Требует решения продукта.
