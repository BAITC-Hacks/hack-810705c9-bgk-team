# Task Match: объединение схемы ADR-004 и актуального workspace

Дата: 2026-09-23. Статус: Proposed. Владелец итоговой схемы: модуль ADR-004.

## Решение

- Единственные рабочие определения — `shared/db/schema.ts`: lifecycle ADR-004,
  score/history ADR-005, team/swipe ADR-006, proposal/stage ADR-007. Alias exports
  ссылаются на те же таблицы, а не создают дополнительные хранилища.
- Идентификаторы задач и команд — `text`: сохраняются slug из main и UUID-строки
  интегрированных PR. Числовые ключи сессий и ходов остаются числовыми.
- Поля оформления команд, timestamps, версия задачи из main сохранены.
- История миграций main (`20260923080214`, `20260923104322`, `20260923112428`) неизменна. После неё
  добавляется одна `20260923113557_task_match_integration`: Drizzle сгенерировал
  DDL и snapshot итоговой схемы, вручную добавлен перенос данных перед удалением
  прежних plural tables. Неопубликованная `20260923110342` удалена.
- В `task.legacyWorkspace` архивируются исходная строка задачи, все девять полей,
  прежние score events, proposals и milestones. Это provenance, а не второе
  рабочее хранилище. Поля `context`, `need`, `contact` переносятся соответственно
  в `context.current`, `context.change`, `link.contact` как `suggested`.
  Групповое подтверждение прежней модели не считается подтверждением нового
  узла. Исходные состояния остаются в архиве. Остальные поля доступны адаптеру
  представления из архива и требуют явного разбора пользователем.
- Старые рейтинги не становятся ADR-005 history. Канонический рейтинг после
  такого переноса равен нулю, поскольку подтверждённых узлов ещё нет. Последующие
  изменения вызывают `recalculateScore`; seed использует ту же функцию.
- Старые отклики сохраняют тексты, ссылки и решения; `selected` становится
  `accepted`. Их сохранённый `fit=0` означает отсутствие рассчитанного нового
  fit на момент переноса; UI должен вычислять текущий fit канонической функцией.
  Не создаются вымышленные criterion rows или ответы на критерии.
- Реальные legacy milestones становятся stage snapshots с ключом
  `legacy:<milestone.id>`, исходными названием, ссылкой, комментарием и временем.
  `submitted` становится `claimed`, `confirmed` сохраняет +10. Пустой threshold
  и пометка в howToCheck обозначают отсутствие структурированного критерия.
  Kickoff принятых legacy откликов сохраняет прежние подтверждённые тексты.
- Оба seed entrypoint используют один idempotent writer. Сохранены main demo
  slug IDs, команды и завершённый school stage; добавлены ADR fixtures и акторы.
  Существующие записи не перезаписываются.

## Ограничения и проверка

По просьбе пользователя после совмещения с main тесты, typecheck, lint, build и
применение миграции не выполнялись. Выполнена только генерация SQL/snapshot и
чтение diff. Перенос заполненной БД и запуск seed остаются непроверенными.
Существующая БД main не изменялась. Локальная временная БД от ранней интеграции
с уже применённой удалённой миграцией не подходит для этой истории: использовать
новую отдельную БД либо исходную историю main после резервного копирования.

## Совмещение с onboarding из main

Миграция main `20260923112428_onboarding_business_logo` и её snapshot сохранены
без изменений. Объединяющая миграция теперь следует за ней, переносит
`businesses.logo_key` в канонический `business.logo_key` и использует snapshot
onboarding как prevId. Прежняя integration-миграция `20260923112352` заменена
до слияния PR в main. Уже созданные временные БД с прежней integration-историей
не обновляются этим изменением автоматически; нужна отдельная согласованная
процедура переноса локального runtime. Этот пересмотр не применялся к БД.
