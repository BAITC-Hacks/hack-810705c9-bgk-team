# ADR-005: Детерминированный рейтинг, уровень, место и история изменений

Дата: 2026-09-23
Статус: Proposed
Владелец: не назначен

## Контекст

Рейтинг 0–100 считает код, а не AI, по 17 узлам (FR-3.1, раздел 6.1, AI-12).
Остальные требования:

- баллы начисляются только за `confirmed` (FR-3.2);
- для бизнеса есть расшифровка, список недостающих сведений и следующий шаг (FR-3.3–3.5);
- пересчёт выполняется после каждого подтверждения и правки (FR-3.6);
- после пересчёта показывается «было → стало», включая место в каталоге (FR-3.7);
- каждое изменение пишется в историю (FR-3.8);
- формат работы и оплата не влияют на рейтинг (FR-3.9);
- рейтинг не зависит от популярности и количества действий (раздел 6.3).

Уровень вычисляется из рейтинга и не хранится (раздел 9.2). Каталог сортируется по
рейтингу (FR-4.4). В колоду попадают задачи с рейтингом ≥ 40 (FR-5.3).

## Решение

1. **`score(card)` — чистая функция** в `src/entities/task/model/score.ts`. На вход
   она получает только поля карточки (`task_field`, `criterion`, `tags_state`
   с тегами). Формат, оплата, свайпы, отклики и длина текста на вход не
   поступают, так что правило раздела 6.3 обеспечивается сигнатурой. Функция
   возвращает `{ total, lines: [{node, points, max, reason}], missing: [{node, weight}], nextStep: {node, gain, levelAfter} }`.
   Правила узлов берутся из таблицы 6.1:
   - «есть число» и «число дней» проверяются регулярками;
   - для `data.sample` засчитываются URL или ≥ 3 строк таблицы;
   - `criteria.items` = Σ по ≤ 3 критериям: 5 баллов с числом в пороге, 2 без числа;
   - ответ «не применимо» даёт 0 баллов, кроме `constraints.other`.
2. **Одна точка записи.** `recalculateScore(tx, taskId, causeNode)` вызывается в
   той же транзакции, что и подтверждение или правка поля, и делает три вещи:
   - считает `score()`;
   - если `total` изменился, обновляет денормализованный `task.score`;
   - вставляет строку `score_event (task_id, before, after, level_before, level_after, node, place_before, place_after, at)`.

   Больше ни один код не пишет в `task.score`.
3. **Уровень не хранится.** `levelOf(score)` — функция с границами 0–39 / 40–69 /
   70–89 / 90–100 (раздел 6.2). Фильтр каталога по уровню переводится в диапазон по
   `task.score`.
4. **Место в каталоге** — ранг задачи среди опубликованных задач по правилу
   FR-4.4: `score DESC`, при равенстве `published_at`. Для неопубликованной
   задачи считается **гипотетическое** место, то есть место, если бы её
   опубликовали сейчас. Только так интерпретируется «6-е место» у черновика в
   Приложении А.
5. **Расшифровка** отдаётся через `GET /api/tasks/:id/score`. Ответ вычисляется
   на лету из `score()` плюс последняя запись `score_event` для панели «было → стало».

## Альтернативы

- **Считать рейтинг только при чтении, без колонки.** Для ~10 задач
  производительность приемлема. Но сортировку каталога и фильтр колоды пришлось бы
  делать в памяти, а «было → стало» всё равно требует снимков. Отклонено в пользу
  кэш-колонки с единственной точкой записи.
- **Рейтинг от LLM или гибридный.** Прямо запрещён FR-3.1 и AI-12.
- **Event sourcing** (рейтинг как свёртка `score_event`). Избыточно для MVP.
  `score_event` остаётся журналом, а не источником истины.

## Последствия

- Плюс: T-6 и T-7 и эталонная последовательность 24 → 44 → 59 → 74 → 77
  проверяются юнит-тестами `score()` на фикстурах.
- Плюс: сортировка каталога и отбор колоды выполняются одним SQL-запросом по `task.score`.
- Минус: `task.score` может разойтись с полями, если кто-то обновит поле в обход
  use-case. Мера: только `recalculateScore` пишет колонку. Для сверки нужна
  dev-проверка «`score()` ≡ `task.score`» по seed.
- Риск: «место» меняется при чужих публикациях без события у этой задачи.
  `place_*` в `score_event` — это снимок на момент изменения, а не live-значение.

## Затронутые модули и проверка

- `presentation-layer`: `src/entities/task/model/{nodes,score,level}.ts`,
  use-case в `src/features/task-card/api`. Таблица `score_event` и колонка
  `task.score` появятся в миграции владельца схемы.
- Проверка:
  - юнит-тесты `score()` по таблице 6.1 и Приложению А (24 / 44 / 59 / 74 / 77)
    и по seed-рейтингам 91 / 76 / 58 / 41 / 27;
  - тест «смена `engagement` → `score` не изменился» (T-7);
  - API-прогон T-6.

## Допущения и открытые вопросы

- Направление вторичной сортировки по дате публикации в FR-4.4 не указано.
  Предложение: более ранняя публикация выше.
- «Место» для неопубликованной задачи — это гипотетическое место (предложение)?
  Нужно подтверждение продукта.
- Seed-карточки должны пройти через `score()`, чтобы получить ровно
  91 / 76 / 58 / 41 / 27. Рейтинг нельзя прописывать в seed числом.
