# ADR-003: Оценка готовности задачи — отдельный агент-оценщик, не шаг воркфлоу

Date: 2026-09-23
Status: Accepted
Owner: team

## Context

Геймификация каталога требует рейтинг задачи 0–100, отражающий готовность
конкретной бизнес-задачи к работе со студентами (а не известность компании):
7 критериев (контекст и потребность 20 / данные и материалы 20 / ожидаемый
результат 15 / критерии успеха 15 / ограничения 10 / пользователи 10 / связь
с бизнесом 10), уровни 0–39 черновик → 40–69 рабочая → 70–89 готовая →
90–100 приоритетная. Баллы — только за заполненные и подтверждённые поля;
низкий рейтинг не прячет задачу и не запрещает отклик; рейтинг пересчитывается
после каждого подтверждённого дополнения.

Первая реализация — шаг `evaluate` внутри воркфлоу `stack1-result-control`
(только цифра, score-only output-процессор). Но пользователь должен иметь
возможность оценить задачу отдельно, прислав её текст агенту напрямую, и
получить не только цифру, а разбор: расшифровку баллов, список недостающих
сведений и пересчёт после редактирования.

## Decision

1. **`taskEvaluatorAgent` — отдельный чат-агент вне воркфлоу.** Пользователь
   сам присылает текст задачи; шаг `evaluate` из `stack1-result-control`
   удалён, цепочка снова `compile → translator-ask → translate`; из
   `schemas/pipeline.ts` убраны `TaskRating`/`RatingOutput`/`Rated` и поле
   `rating` в `FinalOutput` (воркфлоу возвращает только пакет и переводы).
2. **Чеклист — скилл `skills/task-readiness-checklist/SKILL.md`** в единой
   папке скиллов (каноничный Agent Skills / LocalSkillSource): рубрика и
   уровни + quality bar, взятый из четырёх `grill-me-*` скиллов (SMART-линзы,
   role test, swap test, falsification test, coverage map). К агенту подключены
   все пять скиллов; модель — общая `GRILL_MODEL`, пути — общий `SKILLS_DIR`.
3. **Ответ — строгий raw JSON** (ключи английские, текстовые значения на
   языке задачи), формат закреплён zod-схемой `RatingReport`
   (`schemas/rating.ts`): `score` 0–100 + `level`
   (draft/working/ready/priority), `breakdown[]` из 7 критериев
   (сумма `awarded` = `score`), `missing[]` — список недостающих сведений
   (конкретные вопросы заказчику, не парафраз рубрики), `recalculation` —
   пересчёт; если в сообщении нет задачи — `{"error":"no_task", …}`.
4. **Пересчёт через memory-thread** (`sessionMemory`): отчёт предыдущей оценки
   остаётся в треде, повторная отправка задачи → полный пересчёт с нуля +
   «было → стало, Δ, что закрылось». Без истории — первичная оценка.

## Alternatives

- **Оставить шаг `evaluate` в воркфлоу** — оценивает только пакеты пайплайна;
  задачи, собранные вручную, недоступны, и формат «только цифра» не даёт
  расшифровки. Отклонено: оценка нужна как самостоятельный сервис каталога.
- **Только цифра 0–100 (прежний формат, score-only процессор)** — просто, но
  без расшифровки и списка недостающих сведений заказчик не понимает, что
  докрутить для повышения уровня; пересчёт не объясним.
- **Structured output (zod-схема отчёта)** — гарантирует типы, но отчёт
  предназначен человеку в чате; markdown рендерится в UI без доп. слоёв.
  *(Отклонено при ревизии: UI нужен парси́мый ответ — выбран raw JSON +
  zod-схема `RatingReport` как контракт.)*

## Consequences

- (+) Задачу можно оценить в любой момент, без прохождения пайплайна; рейтинг
  пересчитывается после каждого дополнения и объясним (таблица + вопросы).
- (+) Уровень — следствие суммы: агенту запрещено «дотянуть» оценку до уровня.
- (+) Низкий рейтинг ничего не прячет: черновик виден в каталоге, отклик не
  запрещён — это проговорено в чеклисте и инструкциях.
- (−) Пересчёт живёт в memory-thread: вне треда (новый чат) агент честно
  отдаст первичную оценку — UI должен держать один thread на задачу.
- (−) Формат JSON держится на инструкциях агента (схема не передаётся на
  уровень вызова chat'а) — при битом парсинге UI может переспросить; zod
  `RatingReport` готов, чтобы при усилении требований перейти на вызов с
  `structuredOutput`.
