# ADR-008: Демонстрационные роли в cookie, границы доступа и видимость AI-журнала

Дата: 2026-09-23
Статус: Proposed
Владелец: не назначен

## Контекст

Регистрации нет: роль выбирается переключателем в шапке и хранится в cookie
(раздел 3, платформа 9). Права ролей различаются:

- бизнес создаёт задачи и принимает решения;
- команда откликается и сдаёт этапы;
- статусы откликов меняет только бизнес (раздел 9.2).

Журнал `AiLog` «доступен в интерфейсе для демонстрации» (AI-14). В нём лежат
промпт, вход и сырой ответ, то есть текст бизнеса, включая контакт
(`it@logistics.example` в Приложении А). Персональные признаки участников в AI не
передаются (AI-13). Сложные роли, регистрация и пароли вне объёма (раздел 12).

Для демо одного значения роли мало. Нужно знать, **какой** бизнес и **какая**
команда: 5 команд из seed, T-1 требует BotForge, T-18 — две команды. Сейчас в
`presentation-layer` нет ни middleware, ни работы с cookie.

## Решение

1. **Три cookie**, все устанавливаются server action переключателя:
   - `tm_role = business|team`;
   - `tm_actor` — id бизнеса или команды из seed; в шапке выбирается из списка;
   - `tm_view = deck|grid` ([ADR-006](006-recommendations-and-catalog.md)).

   Для `tm_role` и `tm_actor` ставятся `httpOnly`, `sameSite=lax`, `path=/`.
2. **Серверная проверка в каждом use-case, а не только в UI.**
   `getDemoActor()` читает cookie через `next/headers` и возвращает
   `{role, businessId?, teamId?}`. Use-case проверяет владение:
   - `task.business_id` для правок, публикации, решений, закрытия, `confirm` и `return`;
   - `proposal.team_id` для правки отклика и `claim`.

   Роль, не подходящая к действию, получает `403`. Это защищает сценарий от
   ошибок UI. Защитой от злоумышленника это **не** является.
3. **Видимость данных по ролям.**
   - Команда видит опубликованные задачи. Из полей карточки ей показываются только
     `confirmed` (FR-4.1), `suggested` не показываются. Ответы «не применимо»
     видны с пояснением (FR-1.11). Своих откликов и этапов команда видит полностью.
   - Бизнес видит свои задачи во всех состояниях и отклики на них. Чужие
     опубликованные задачи бизнес видит только как каталог.
   - «Вид исполнителя» (FR-2.8) использует тот же серверный фильтр, что и роль
     команды, а не отдельную вёрстку.
4. **AI-журнал** доступен роли `business` и только по своим задачам
   (`GET /api/ai-log?taskId=`). Состав описан в [ADR-003](003-ai-layer-contract.md).
   Секретов и env в журнале нет. Данные команд в AI не отправляются, поэтому
   журнал их не содержит. Отдельной маскировки контакта в журнале нет: это текст,
   который бизнес сам написал в своей задаче.
5. **Явная пометка в README и UI:** «демо-режим, без аутентификации». Cookie можно
   подделать, поэтому развёртывание за пределами локального демо не допускается
   без замены механизма.

## Альтернативы

- **Только `tm_role`, «текущий» бизнес или команда фиксированы.** Не покрывает
  T-18 (выбор двух команд, у каждой свои этапы) и демо с BotForge против DataBrew.
  Отклонено.
- **Проверки только в UI** (скрытие кнопок). Одно неверное состояние клиента
  ломает инварианты FR-7.7 и раздела 9.2. Отклонено.
- **Настоящая аутентификация** (например Better Auth). Вне объёма (раздел 12), а
  на 5 часов слишком дорого.
- **Подписанные cookie (HMAC).** Недорого, но в локальном демо не даёт реальной
  пользы. Можно добавить, если демо будет публичным.
- **Журнал AI открыт всем ролям.** Упрощает показ, но раскрывает командам текст
  чужих черновиков и неподтверждённые поля. Отклонено.

## Последствия

- Плюс: одна функция `getDemoActor()` задаёт границу доступа для всех маршрутов,
  проверки тестируются на уровне use-case.
- Плюс: на демо можно мгновенно переключаться между бизнесом и командами.
- Минус: безопасности нет. Решение пригодно только для локальной демонстрации.
- Риск: забыть проверку владения в новом маршруте. Мера: use-case принимает
  `actor` обязательным аргументом.

## Затронутые модули и проверка

- `presentation-layer`: `src/shared/lib/demo-actor.ts`, переключатель в шапке
  (`src/features/demo-role-switch`, подключается в `src/_app`), все use-case из ADR-004–007.
- Проверка:
  - API-прогон: роль `team` вызывает `POST /proposals/:id/decision` → `403`;
  - команда A делает `claim` этапа команды B → `403`;
  - роль `team` вызывает `GET /api/ai-log` → `403`;
  - UI: после перезагрузки сохраняются роль и вид.

## Допущения и открытые вопросы

- Сколько бизнесов в seed? В ТЗ Business есть в сущностях (9.1), но не в таблице
  тестовых данных (9.3). Предложение: по одному на каждую карточку, либо один
  демо-бизнес на все пять.
- Нужен ли журнал AI в демо и для чужих задач (например показать «отброшенное
  поле» на seed-задаче)? Предложение: демо идёт под ролью владельца задачи.
