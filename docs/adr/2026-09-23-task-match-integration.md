## Принятые интеграционные решения

- Актуальный frontend из main сохраняет приоритет: workspace, оформление,
  голосовой ввод и локальные UI-инструменты сохраняются. Адаптеры BFF связывают
  этот интерфейс с каноническими данными. Ссылки из main ведут на `/task-match`
  для полного сценария прожарки, откликов с критериями, kickoff и этапов.
  Локальные подсказки чата обозначены как локальные и не представляются live AI.
- Жизненный цикл задачи, прожарки, полей и критериев принадлежит ADR-004.
  `score`, объяснение и история принадлежат ADR-005, `fit` — ADR-006,
  отклики, kickoff и этапы — ADR-007, проверки актёра — ADR-008.
- Каталог и рекомендации используют сохранённый канонический рейтинг.
  Команда получает только разрешённые поля и свои отклики; владелец задачи
  получает редактор, прожарку и AI-лог.
- Изменение/подтверждение поля пересчитывает рейтинг и сохраняет историю в
  той же транзакции. Принятие отклика фиксирует kickoff и критерии этапов.
  Баллы появляются после бизнес-подтверждения этапа, повторное подтверждение
  не начисляет их повторно.
- Mastra вызывается через `@mastra/client-js` и `MASTRA_API_URL`; inference
  выполняется вне транзакции бизнес-данных. Прямых вызовов модели из UI нет.
- Адаптеры `/api/workspace/*` сохраняют DTO актуального UI, вызывая
  канонические операции записи, решений и этапов. Групповое сохранение полей
  блокирует строку задачи, проверяет версию и пересчитывает рейтинг.
  Сложное редактирование нескольких узлов/критериев возвращает 422 с указанием
  открыть подробный редактор, вместо потери структуры данных.
- Сессия workspace синхронизирована с каноническими `tm_role`/`tm_actor`.
  Общие обработчики сохраняют ошибки, проверку Origin (403), ограничение тела
  (413) и Content-Type (415). Эта часть выполнена с участием Claude Code;
  факт выполнения изменений не означает прохождение проверок.

## Итоговая схема и переход с main

Сохранены история users и миграция workspace из main. Единая последующая
миграция `20260923112352` сводит таблицы и ключи в каноническую схему.
Raw JSON/заметки и история старого рейтинга сохраняются. Только три legacy-поля
получают прямое соответствие каноническим узлам; они становятся `suggested`,
а канонический рейтинг равен 0 до подтверждения. Остальные девять UI-групп не
выдаются за полностью подтверждённые семнадцать узлов. Legacy milestones
переносятся в этапы с 10 баллами для подтверждённых результатов; legacy fit
пересчитывается канонической функцией при чтении. Seed включает оба набора
демо-данных.

Произвольные прежние `businessId` не входят в статический allowlist демо-актёров.
Для редактирования таких задач нужен явный маппинг владельца. Интеграция не
назначает эти задачи произвольному бизнесу автоматически. Штатные seeded
бизнесы и команды main добавлены в allowlist.

Это описание подготовленного преобразования; миграция не запускалась после
финального merge и не объявляется проверенной на заполненной базе.

## ADR-003 и ADR-009: конкретные блокеры

PR #12 и #14 используют stateful workflow с suspend/resume и LLM-оценку
готовности. Контракт интегрируемого BFF требует stateless `analyze-text` /
`phrase-question`, а рейтинг рассчитывается детерминированным кодом.
Эти PR не подменяют работающий fallback; live AI-сценарий остаётся неподтверждён.

PR #15 полезен общими Zod-контрактами и разделением входной ошибки 422 от
ошибки формы серверного ответа 500. Его полное подключение вернуло бы
`globalThis`/Map-хранилище, собственные score/fit, actor-заглушку и отдельные
use-case. Контракты также требуют адаптации: `draftText/format` против текущих
`description/engagement`, checkpoint без `sessionVersion`/`draft`, строковый
`sourceTurnId` вместо serial, массив `criteriaAnswers` вместо версионированного
объекта. PR #15 не объявляется целиком интегрированным. Перенесена минимальная полезная
идея: проверка серверного score-ответа через `safeParse` возвращает 500 при
нарушении схемы. Полный общий контракт ADR-009 остаётся отдельной работой;
Map-runtime и заменяющие доменную логику use-case из PR не подключены.

## Проверки и пределы результата

До финального совмещения с новым main выполнены:

- typecheck и адресные lint-проверки;
- unit: рейтинг — 48, прожарка — 6, каталог/fit — 25,
  отклики/этапы — 23, актёр/доступ — 22;
- интеграция пересчёта с PostgreSQL — 5 проверок;
- 108 HTTP-проверок на изолированной БД `task_match_integration`:
  checkpoint и версия, рейтинг/история, публикация, видимость и запреты,
  рекомендации/skip, отклики двух команд, принятие и kickoff,
  claim → return → claim → confirm, запрет повторного начисления.

HTTP-прогон выполнялся при `AI_ENABLED=false`: он подтверждал DB/BFF и fallback,
но не live Mastra, модель или production-инфраструктуру. Использовалась отдельная
локальная БД; общие и production БД не мигрировались.

После просьбы пользователя «без тестов» новые тесты не запускаются.
Результат финального merge main, адаптеры нового frontend и итоговая миграция
не покрыты указанными выше результатами. Upgrade уже заполненной workspace-БД
и чистая установка итоговой схемы после merge остаются непроверенными.
Старый `scripts/test-backend.ts` из main проверяет прежние DTO и формулу девяти
полей и не является приёмочным gate этой ветки. Результат `integration-http.ts`
относится только к состоянию до merge.

PR остаётся draft. Следующий владелец должен проверить маппинг legacy-владельцев,
просмотреть SQL и сохранность исходных данных, затем отдельно проверить upgrade,
чистую установку и оба UI-пути на итоговом commit. Подключение согласованного
live Mastra и завершение ADR-009 требуют отдельной работы.
